# Backend Atlas — один кандидат

Атлас технологий, учебного плана, вопросов, задач и интервью. Работает автономно и с приватным сервером синхронизации. В серверном профиле ровно один кандидат.

## Текущее размещение

- Атлас: https://bkrasnov.github.io/backend-atlas/
- Адрес API в настройках атласа: `https://bdkrasnov-developer.ru/atlas-api`
- На VPS API работает как служба `backend-atlas` и слушает только `127.0.0.1:3341`. Nginx передаёт к ней запросы из `/atlas-api/`.
- Существующий фронтенд в корне `bdkrasnov-developer.ru` сохраняет свои файлы и маршруты.
- Данные: `/var/lib/backend-atlas/workspace.json`; предыдущая версия — соседний `.bak`.
- Ключ находится на VPS в `/etc/backend-atlas.env`, в поле `ATLAS_TOKEN`. Его значения в репозитории нет.

При первом открытии сайта появится обязательное окно «Вход в Backend Atlas». Введите ключ: сервер проверит доступ, загрузит сохранённый профиль и откроет атлас. До проверки атлас скрыт и заблокирован; Escape и клик снаружи не закрывают вход. Ключ запоминается в этом браузере и проверяется автоматически при следующих посещениях. «Отключить» снова блокирует атлас. Для переноса отметок из старого локального HTML после входа импортируйте его JSON и отправьте профиль на сервер.

Для этой схемы используется `deploy/provision-existing-nginx.py`: он устанавливает отдельный Node.js 24, службу systemd и маршрут из `deploy/nginx-atlas-api.conf`. Системный Node.js не заменяется. Обновление принимает архив проекта и SHA релиза, сохраняет существующий ключ и хранилище, проверяет работоспособность API и Nginx перед подключением маршрута.

Проверка службы на VPS:

```sh
systemctl status backend-atlas --no-pager
journalctl -u backend-atlas -n 50 --no-pager
```

## Варианты размещения

| Вариант | Где находится интерфейс | Где хранятся данные |
| --- | --- | --- |
| VPS | На вашем домене | На диске VPS и локально в браузере |
| GitHub Pages без API | `https://owner.github.io/repository/` | В браузере; перенос через HTML/JSON |
| GitHub Pages + VPS API | На GitHub Pages | На VPS и в браузере |

[GitHub Pages — статический хостинг](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). Запустить Node.js-бэкенд непосредственно на `github.io` нельзя. Для синхронизации интерфейса на Pages нужен отдельный VPS с HTTPS.

## Локальный запуск

Нужен Node.js 22 или новее. `npm install` не нужен: у приложения нет внешних runtime-зависимостей.

```sh
npm run setup
npm run build
npm start
```

Откройте `http://127.0.0.1:3000`. В окне входа введите значение `ATLAS_TOKEN` из созданного `.env`. Ключ намеренно не выводится в терминал. Существующий серверный профиль загружается автоматически; если хранилище пустое, создаётся первый профиль. Для ручного переноса между сервером и локальной копией доступны настройки «Сервер и синхронизация».

После первого подключения адрес, ключ и подтверждённая ревизия сохраняются в localStorage этого браузера. После перезагрузки атлас автоматически проверяет ключ и запрашивает актуальные данные с VPS; до успешного ответа локальный кэш не показывается. После проверки продолжается автосохранение. «Отключить» удаляет сохранённый ключ; очистка данных сайта также отключает автоматический вход. На новом устройстве ключ вводится один раз. Ключ не входит в HTML/JSON-экспорты; его нельзя вставлять в исходники, настройки GitHub Pages или репозиторий.

Неотправленные локальные правки отмечаются до отправки и переживают перезагрузку. После восстановления связи они отправляются автоматически, если серверная ревизия не изменилась. При изменениях с другого устройства синхронизация останавливается с сообщением о конфликте: обе копии сохраняются, источник данных выбирается в настройках синхронизации. Сетевые ошибки повторяются с задержкой от 2 до 30 секунд; неверный ключ удаляется из сохранённого подключения.

Адрес сервера может содержать префикс пути, например `https://example.com/atlas-api`. В GitHub Actions можно задать переменную репозитория `ATLAS_API_URL` с этим адресом: он появится в настройках опубликованного атласа автоматически. Это публичный адрес, а не ключ доступа.

Данные, ранее заполненные в локальном `file://` HTML, браузер может хранить отдельно от сайта. Сохраните из прежнего атласа JSON и импортируйте его в размещённую версию, затем отправьте профиль на сервер.

## VPS: Docker Compose и HTTPS

Подходит Linux VPS с Docker Engine, плагином Docker Compose и `openssl`. [Инструкция установки Docker](https://docs.docker.com/engine/install/). Существующие конфигурации других приложений скрипт не меняет.

1. Направьте DNS-запись домена, например `atlas.example.com`, на IP VPS. Если опубликована AAAA-запись, она тоже должна указывать на этот VPS. Откройте TCP-порты 80 и 443; UDP 443 опционален. Они должны быть свободны для Caddy. Если там уже работает ваш reverse proxy, подключите атлас к нему вместо второго Caddy.
2. Скопируйте проект или распакуйте подготовленный архив на VPS:

```sh
mkdir -p ~/backend-atlas
tar -xzf backend-atlas-deploy.tar.gz -C ~/backend-atlas
cd ~/backend-atlas
bash scripts/deploy-vps.sh atlas.example.com
```

Для фронтенда на GitHub Pages разрешите его origin при первом запуске:

```sh
bash scripts/deploy-vps.sh atlas.example.com https://OWNER.github.io
```

Указывается origin без пути `/repository/`. Если `.env` уже существует, скрипт его сохраняет. Для смены домена или добавления origin отредактируйте `.env` самостоятельно и повторите деплой. `ATLAS_TOKEN` должен быть случайным ключом не короче 32 символов; скрипт генерирует 64 шестнадцатеричных символа.

```sh
docker compose ps
docker compose logs --tail=80 atlas caddy
```

Откройте `https://atlas.example.com`. Caddy получает и обновляет TLS-сертификат автоматически при корректных DNS и доступности портов. [Условия автоматического HTTPS](https://caddyserver.com/docs/automatic-https).

`atlas` не публикует порт 3000 наружу. Данные хранятся в именованном volume `backend-atlas_atlas-data`; перезапуск и пересборка его сохраняют. `docker compose down` останавливает проект. Не используйте `down -v`, если данные нужны.

Обновление: замените файлы кода и снова выполните `bash scripts/deploy-vps.sh atlas.example.com`. `.env` и volume остаются прежними. Запускайте один экземпляр API на один файл данных: межпроцессная запись в общее хранилище не поддерживается.

## GitHub Pages

В проекте уже есть `.github/workflows/pages.yml`. Он публикует **только** содержимое `public/`, а не весь репозиторий. Сборка исключает встроенный профиль `atlas-profile-data`. Файлы `.env`, серверные данные, тестовые артефакты и ключ не попадают в публикацию.

1. Создайте свой GitHub-репозиторий и загрузите исходники проекта. Не загружайте `.env`, `data/` и `output/`.
2. В **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**.
3. Push в ветку `main` запускает публикацию автоматически. Можно запустить workflow вручную во вкладке Actions.

Дополнительный скрипт запуска workflow через [GitHub CLI](https://cli.github.com/):

```sh
gh auth login
npm run deploy:pages -- OWNER/REPOSITORY main
```

Workflow должен уже находиться в указанной ветке репозитория. Скрипт запускает публикацию, а не создаёт репозиторий и не загружает исходники. [Документация workflow GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

После публикации можно пользоваться локальным режимом. Для синхронизации откройте «Сервер и синхронизация» и укажите `https://atlas.example.com`. В `.env` VPS добавьте `ALLOWED_ORIGINS=https://OWNER.github.io` и пересоздайте контейнер через скрипт деплоя. Несколько разрешённых origin перечисляются через запятую. API не разрешает `*` или `null`; для работы с сервером открывайте размещённый сайт, а не локальный `file://` файл.

## Сохранение, конфликты и резервные копии

- Изменения сначала сохраняются в браузере. После подключения API — также отправляются на сервер с задержкой 800 мс.
- При конфликте ревизий автоматическая отправка приостанавливается. Откройте синхронизацию, скачайте локальную копию, повторно проверьте сервер и выберите нужную версию. Автоматического смешивания ответов нет.
- Перед загрузкой серверной версии сохраняется локальная резервная копия. Она доступна кнопкой «Копия до загрузки с сервера».
- «Сохранить атлас · HTML» сохраняет переносимый автономный файл с данными. Ключ доступа в него не попадает. Для обновления такого файла скачайте HTML снова.
- API пишет `/data/workspace.json` атомарной заменой. `/data/workspace.json.bak` хранит предыдущую версию; это защита от неудачной замены, а не история всех изменений.
- Для независимой резервной копии используйте JSON-экспорт атласа или копирование файла из контейнера:

```sh
mkdir -p backups
docker compose cp atlas:/data/workspace.json ./backups/workspace.json
```

Импортировать профиль проще через интерфейс. Для восстановления серверного файла остановите API, восстановите правильный JSON-снимок с полями `revision`, `workspace`, `updatedAt`, затем запустите API. Обычный JSON-экспорт атласа отличается от внутреннего файла сервера и импортируется через интерфейс.

## API

| Запрос | Назначение |
| --- | --- |
| `GET /api/health` | Проверка доступности без данных профиля |
| `GET /api/workspace` | `{ revision, updatedAt, workspace }` и заголовок `ETag` |
| `PUT /api/workspace` | JSON самого workspace; обязателен `If-Match: "revision"` |

Для workspace требуется `Authorization: Bearer <ATLAS_TOKEN>`. Начальная ревизия пустого хранилища — `0`; `workspace` равен `null`. Успешная запись увеличивает ревизию. `409` — конфликт; `428` — не передана версия; `401` — неверный ключ; `403` — запрещённый origin. Размер запроса ограничен 20 МБ.

Переменные окружения описаны в `.env.example`. В Docker host и путь данных заданы образцом контейнера; `PUBLIC_ORIGIN` Compose формирует из `ATLAS_DOMAIN`. Хранилище не публикуется статическим сервером. Комментарии интервьюера доступны владельцу ключа и входят в полный HTML/JSON.

## Проверки и сборка архива

```sh
npm run build
npm test
docker compose --env-file .env config --quiet
npm run package
```

Браузерная проверка: `npm run test:browser`. Для неё отдельно нужен Playwright с Chromium либо Microsoft Edge. При необходимости задайте `PLAYWRIGHT_MODULE` как путь к модулю и `BROWSER_CHANNEL` как имя браузерного канала. Тест запускает временный сервер и закрывает браузер и сервер после проверки.

Проект подготовлен и проверен локально. Выпуск реального TLS-сертификата и публикация workflow проверяются на домене и в GitHub-репозитории владельца.
